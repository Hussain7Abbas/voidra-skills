# Prototypes that answer a question

Name the question and success signal before building: state/logic behavior versus visual
structure. Choose the smallest useful fidelity. A state demo exposes readable state and
awkward transitions; a UI comparison varies structure while keeping surrounding data and
context comparable. Multiple variants are optional, not routine deliverables.

Use synthetic or read-only data and isolate mutations from production. Keep prototypes
clearly identified; preserve the project's actual routing/build conventions and supported
toolchain. Tests/polish should match experiment risk, not blanket production checklists.

Capture what was learned, its limits and a pointer to the experiment in the existing issue
or decision source. Promote only validated decisions, with production quality checks for
any reused code. No automatic prototype branch, commit, publication, or new artifact scheme.

Reference: [GOV.UK prototyping](https://www.gov.uk/service-manual/design/making-prototypes).
