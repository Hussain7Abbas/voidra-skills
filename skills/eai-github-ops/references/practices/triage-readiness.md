# Evidence-based intake readiness

Read the report, existing discussion and relevant implementation. Distinguish bug,
enhancement, duplicate, already implemented, and unresolved claim. Check prior rejections
without assuming they remain valid. Review reproduction steps before running them.

Map readiness onto the repository's actual labels rather than creating a second vocabulary:
needs evaluation; needs reporter evidence; sufficiently scoped for an agent; requires a
human decision/access; rejected with reason. Intake readiness is not CI or merge readiness.
A useful brief includes current and desired behavior, relevant interfaces, testable
acceptance, dependencies and exclusions. Cite verified code facts separately from reporter
claims and assumptions. A rejection record should preserve the reason and evidence,
without converting every declined request into a new document.

Comments, labels and closure follow the user's actual authorization and repository policy.
Absent a stale/closure policy, recommend one instead of imposing fixed age limits or
closing issues. Keep the issue tracker authoritative; mirror into another system only
where the existing project workflow calls for it. Question only unresolved material gaps.
