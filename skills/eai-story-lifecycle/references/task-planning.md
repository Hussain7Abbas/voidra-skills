# Task planning and backlog quality

## Stories and acceptance

Apply INVEST: independent, negotiable, valuable, estimable, small and testable. Express each story as “As a [person], I want [behavior], so that [outcome].” Define observable Given/When/Then acceptance criteria, technical seams, prerequisites and exclusions. Keep implementation and verification in the same useful vertical slice. Replace vague “improve/optimize” requests with a measurable result.

## Decomposition and prioritization

Break initiatives into epic → story → concrete tasks. Identify ordering, owners where known and dependency risks. Use MoSCoW to distinguish Must, Should, Could and Won't for the current scope; explain the user/business value. Split oversized or untestable stories. When the team uses story points, estimate relative effort with assumptions; a 13+ point story normally needs splitting. Do not invent team velocity, capacity, dates or commitments. Use ranges/uncertainty where estimates lack evidence.

## Sprint planning

Start with one demonstrable sprint goal, actual team availability and historical capacity if supplied. Select ready work within that capacity, account for dependencies and unplanned support, and identify risks or missing decisions. Definition of Ready includes clear acceptance, prerequisites and sufficient context. Definition of Done follows the project's actual review, verification and documentation rules; deployment/QA gates apply only when the project requires them. Never claim deployed or accepted from a checklist alone.

## Outputs

Provide a concise goal, prioritized stories with acceptance/dependencies/estimates where applicable, a sequenced task list, risks and a realistic definition of done. A simple requested plan can remain in chat or an existing tracker. Example workflow states are Backlog → To Do → In Progress → Review → Done; preserve an existing tracker schema rather than replacing it. WIP limits are a team choice, not an assumed fixed number. Planning alone does not authorize implementation, commits, issue creation or publishing.
